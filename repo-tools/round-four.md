## Original witnesses

- Linux key update exceeded 30 seconds on [attempt one](https://github.com/ZSeanYves/http/actions/runs/45640592316/job/139297838354) and [attempt two](https://github.com/ZSeanYves/http/actions/runs/45640592316/job/139306176004). Neither historical run retained packet events. The same failure recurred on [instrumented Linux](https://github.com/ZSeanYves/http/actions/runs/45649197228) and macOS. After receiving response headers the pinned aioquic client immediately replaces both directions' keys. Its only new-phase packet is ACK-only. The configured loss drops that datagram, leaving the server on the previous phase. The client discards the retransmissions until the original 30-second deadline; both proxy queues drain. The historical runs are consistent with this diagnosis.
- Direct, loss-only and reorder-only control runs each passed twice on macOS. A separate copy of the pinned peer retaining its previous read context until it authenticates a new-phase packet passed 20/20 combined-profile repetitions. The original peer has its own required job. The reference patch applies only to the separately fingerprinted fixture. See [RFC 9001 §6.1](https://www.rfc-editor.org/rfc/rfc9001.html#section-6.1) and [the pinned peer's receive key transition](https://github.com/aiortc/aioquic/blob/b541fe0d30e03799214cfb2ba6e15101390e6a3f/src/aioquic/quic/crypto.py#L246).
- Before hot-path changes, the corrected Go probe counted every successful request in its latency distribution. On the audit M4, H1 MoonBit windows measured 891.7/909.2 requests per second and 4.769/4.419 ms p95. H2 measured 874.5/825.3 and 6.223/6.473 ms. All eight Go/MoonBit windows verified the protocol, status and bytes. Final acceptance repeats baseline and candidate in alternating order on the same host.
